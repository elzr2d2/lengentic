# Parallel execution playbook

How to run the LenGentic harness with more than one agent at a time without the token bill
or the quality dropping. Companion to `docs/PROJECT_STATUS.md`, which is generated by
`pnpm oracle md` and is the authority on what is actually done.

`MVP_PLAN_V3.md` §8 and `CLAUDE.md` still bind: one phase at a time, no automatic
progression, human approval at every phase gate. Parallelism happens **inside** a phase,
never across one.

---

## 1. The oracle decides the fan-out, not you

```bash
pnpm oracle status          # phase progress, open decisions, what is unblocked now
pnpm oracle unblock         # root causes of everything blocked, ranked by leverage
pnpm oracle waves 2         # the parallel batches for phase 2, plus lane collisions
pnpm oracle packet <id>     # a ready-to-dispatch work packet with the contract sliced in
```

`unblock` is the one to run when the matrix looks discouraging. Forty blocked deliverables
is not forty problems — it is nine, and two of them are worth more than the other seven put
together. See §10.

A wave is the set of deliverables with no dependency on each other. Dispatching wider than
the wave does not go faster — the extra agents are working against files that do not exist
yet, and you pay for their confusion twice: once for the wrong output, once for the repair.

Phase 2's shape, as the oracle currently computes it:

```text
WAVE 1   1 agent    p2.shared-schema          ← everything is behind this
WAVE 2   3 agents   merge-rules | prisma-run-step | sdk-core
WAVE 3   3 agents   ingest-endpoint | runs-api | sdk-injection     ← lane collision
WAVE 4   2 agents   idempotency | dashboard-runs
WAVE 5   1 agent    integration-tests (Validator)
```

Peak useful parallelism in this project is **three**. It is not five, and it is never one
agent per work package in the plan's table — the plan's five packages are not five
independent things.

## 2. Model tiering — the largest single lever

`MVP_PLAN_V3.md` §9 assigns models per role. The shipped `.claude/agents/*.md` files do not
match it:

| Role      | Plan §9     | `.claude/agents/*.md` | Runs how often              |
| --------- | ----------- | --------------------- | --------------------------- |
| Architect | Opus High   | `opus`                | Rare — escalation only      |
| Builder   | Sonnet High | `sonnet`              | Every packet                |
| Validator | Sonnet      | **`opus`**            | Every packet — the hot path |
| Reviewer  | Sonnet High | **`opus`**            | Phase gates                 |

Validator on Opus is the expensive line, because Validator runs after every executable work
packet while Architect runs almost never. Its job — run commands, capture real output,
design adversarial cases — is execution-shaped, and Sonnet does it well.

Recommended, in priority order:

1. **Validator → `sonnet`.** Matches the plan. Biggest saving, smallest risk.
2. **Reviewer stays `opus` only if it stays rare.** The plan says Sonnet High; Opus is
   defensible for a phase gate that runs once per phase, and indefensible if Reviewer starts
   running per packet. §9 already forbids the latter: _"Do not run Architect, Validator, and
   Reviewer after every minor edit."_
3. **Architect stays `opus`.** It is escalation. If it runs often, the problem is routing,
   not cost.

## 3. Slice the contract, do not ship the plan

`MVP_PLAN_V3.md` is roughly 25k tokens. A subagent that reads it to implement one merge rule
spends 25k tokens to acquire about 1k of constraint, and pays it again on every retry and
every agent in the wave.

`pnpm oracle packet p2.merge-rules` emits ~900 tokens: the deliverable, its dependencies,
any open decision that gates it, and §12 verbatim. Same constraint, same verbatim wording,
without the other twenty-five sections.

Rough arithmetic for Phase 2 — 10 deliverables, one Builder each:

```text
whole plan per agent     10 × 25k  = 250k tokens, before a line of code is written
sliced packets           10 × ~1k  =  10k tokens
```

The saving compounds with retries, and it also improves output: an agent given §12 alone
cannot drift into re-litigating §18.

**Rule: no subagent is ever told "read MVP_PLAN_V3.md".** It gets a packet.

## 4. Watch the lane collisions

`pnpm oracle waves` flags when two nodes in the same wave live in the same directory. Phase
2 wave 3 has one:

```text
wave 3  lane api  p2.ingest-endpoint + p2.runs-api
```

Two Builders editing `platform/api/src` concurrently is the most expensive failure mode
available: you pay for both agents, then pay a third time to reconcile them, and the
reconciliation is exactly the kind of merge a model does badly. Options, cheapest first:

1. **Serialise them.** Wave 3 becomes two agents plus one follow-on. Usually right.
2. **Give one a git worktree** (`isolation: "worktree"`). Correct when both are large.
3. **Split the lane** so each owns a distinct module directory.

Never dispatch a colliding pair into the same working tree and hope.

## 5. Validate per wave, review per phase

The default loop in §9 is per work packet. At three-wide, run it per **wave**:

```text
dispatch wave (1-3 Builders, parallel, one message)
  → pnpm gates                      ← zero tokens, catches lint/type/boundary/test
  → one Validator over the wave's combined diff
  → Builder repairs validated failures
  → next wave
      ...
  → Reviewer once, at the phase gate
  → pnpm gates:full
  → human approval
```

Three Builders and three Validators per wave is six agents to deliver three things. One
Validator sees the whole wave's diff and catches interaction defects that three
single-packet Validators each miss by construction.

**Run `pnpm gates` before any validation agent, always.** Lint, typecheck, boundaries and
tests cost nothing and catch a large share of what a Validator would otherwise spend tokens
discovering. `CLAUDE.md` already states the principle: never ask an agent to verify what a
script can verify.

## 6. Batch the dispatch

Send a wave's agents as multiple tool calls in a **single message**. Sequential dispatch
serialises the wall clock for no benefit, and it breaks prompt-cache reuse across the
agent-definition prefix that all three Builders share.

Keep each agent's prompt prefix stable — same agent file, same standing rules, packet last.
Varying the prefix per agent defeats caching on the part that is identical anyway.

## 7. Open decisions are hard stops, not defaults

Six decisions in `MVP_PLAN_V3.md` are unanswered, and four of them gate Phase 2 work:

```text
OD-1  STALE_RUN_THRESHOLD         → p2.prisma-run-step, p2.runs-api
OD-2  ingestion limits            → p2.ingest-endpoint, p2.sdk-core
OD-3  conflicting terminal states → p2.merge-rules
OD-5  handoff retrofit timing     → p1.debt.handoff-files
OD-6  pre-commit + secrets        → p1.debt.precommit, p1.debt.secrets
```

`pnpm oracle packet` puts a **STOP** block at the top of any packet a decision gates, and
tells the agent to report `BLOCKED` rather than pick a default. This is deliberate: an agent
that silently defaults `STALE_RUN_THRESHOLD` to five minutes has changed which runs enter
aggregation — a product decision, made invisibly, discovered in Phase 5.

Answer the four Phase 2 decisions before dispatching wave 2. It is a five-minute
conversation that unblocks three parallel agents. Mark them `"answered": true` in
`scripts/oracle/graph.json` and the oracle stops flagging them.

## 8. Findings the dependency graph surfaced

Three things fall out of the graph that are not visible in the plan's phase ordering.

### `p5.engine-pkg` is unblocked right now

The analysis engine depends on nothing from Phases 2, 3, or 4 — §18's aggregation and §19's
gates are pure functions over fixtures, already proven by the Phase 0 spike. It could run
fully parallel with all of Phase 2.

**It should not, without a human decision.** `CLAUDE.md` says work one phase at a time and
never automatically begin the next. The graph says the constraint is process, not
technology. That is a trade worth making consciously: parallelising it would compress the
critical path materially, and it would also mean two phases in flight, which is exactly what
the phase discipline exists to prevent. Raised, not taken.

### Clock/IdGenerator is scheduled one phase late

§17's `Clock` and `IdGenerator` are injection seams **in the SDK**, but v3 assigns "Seeded
Clock/IdGen" to Phase 3 WP4. If Phase 2 ships the SDK without the seams, Phase 3 reopens
Phase 2 code to add them — and Phase 2 has already passed its gate by then.

The graph models this as `p2.sdk-injection`, in Phase 2, wave 3. Land the seams with the
SDK; Phase 3 supplies the seeded _implementations_, which is what it should have been
scoped to all along.

### §23 Run Summary has no phase

It appears in the final Definition of Done (§24) and in §23, but no phase's work-package
table owns it. The graph assigns it to Phase 4 (`p4.run-summary`) since it aggregates the
Phase 4 entities. One caveat: its `Repeated failed actions` line depends on the Phase 5
analyzer, so ship that one field last or the summary renders a column it cannot populate.

## 9. Unblocking, in leverage order

`pnpm oracle unblock` traces every blocked deliverable to a root cause a human can act on
today. Forty blocked nodes currently reduce to nine causes:

```text
DISPATCH  p2.shared-schema   unblocks 32     the Zod wire contract
DECIDE    OD-2               unblocks 22     ingestion limits
DECIDE    OD-1               unblocks 19     STALE_RUN_THRESHOLD
DISPATCH  p5.engine-pkg      unblocks 15     analysis-engine package
DECIDE    OD-4               unblocks  9     repeated-failed target/operation
ENV       env.docker         unblocks  5     Docker daemon
DECIDE    OD-3               unblocks  5     conflicting terminal states
DECIDE    OD-6               unblocks  2     pre-commit + secret detection
DECIDE    OD-5               unblocks  1     handoff retrofit timing
```

Three kinds of cause, three kinds of fix.

### DECIDE — six answers, one sitting

Every one of the six already has a proposal written into `MVP_PLAN_V3.md`. None needs
research; they need a human to say yes. Confirming all six unblocks more than answering any
five of them individually, because OD-1/2/3 gate the same Phase 2 wave.

Mechanically: set `"answered": true` on the decision in `scripts/oracle/graph.json`, record
the answer in the plan, and the STOP block disappears from the affected packets.

Do **not** let an agent default these. `pnpm oracle packet` deliberately refuses: an agent
that quietly picks a five-minute `STALE_RUN_THRESHOLD` has changed which runs enter
aggregation — a product decision, made invisibly, surfacing in Phase 5 as a wrong number.

### DISPATCH — two roots carry the whole graph

`p2.shared-schema` gates 32 of the 40. It is one package of Zod schemas from §12, it is
already fully specified, and nothing else in Phase 2 can be parallelised until it lands.
Everything else in the project is downstream of one afternoon's work. Build it first, alone,
and review it properly — 32 deliverables inherit its mistakes.

`p5.engine-pkg` gates 15 more and is **already unblocked**. It depends on nothing in Phases
2–4. Running it now means two phases in flight, which `CLAUDE.md` forbids; the graph is
reporting that the constraint is process, not technology. That is a legitimate trade to make
deliberately — it is not one to drift into.

### ENV — the Docker gap has a cheaper fix than installing Docker

`env.docker` blocks five deliverables and `BACKLOG.md` records the cost: WSL2 plus Docker
Desktop, elevated install, reboot. But `.github/workflows/ci.yml` already contains a
`docker` job that does precisely the blocked checks:

```yaml
docker compose up -d --wait --wait-timeout 180
curl -fsS http://localhost:3001/health # API healthcheck gates on a reachable database
```

and an `integration` job that runs Testcontainers on the runner's daemon. GitHub's runners
ship Docker. The workflow has simply never executed, because `git remote -v` is empty.

Three routes, cheapest first:

| Route                  | Cost                          | Closes                                                          |
| ---------------------- | ----------------------------- | --------------------------------------------------------------- |
| **Push to a remote**   | Create the repo, push         | All four Phase 1 items, plus `pnpm test:integration`, in CI     |
| Install Docker locally | WSL2 + Docker Desktop, reboot | Same, plus a local loop for Phases 2–7                          |
| Native PostgreSQL      | Install PG, point tests at it | Integration tests only — **not** "`docker compose up` succeeds" |

Route 1 is close to free and this is a portfolio project that wants a public repository
anyway. Its limitation is real, though: every Phase 2+ integration test becomes a push-and-
wait loop instead of a local one, which is a poor inner loop for the four phases that lean
hardest on the database. Route 2 is the better answer if Phases 2–7 are actually going to be
built; Route 1 is the better answer if the goal is to close Phase 1 today.

They are not exclusive. Route 1 now closes Phase 1; Route 2 before Phase 2 starts gives the
inner loop back.

Whichever runs, the evidence belongs on disk — `p1.docker-runtime` probes for
`.artifacts/oracle/docker-smoke.ok`. Drop the CI run URL or the local compose output in it.
A green pipeline nobody recorded is not evidence next month.

## 10. What this playbook does not claim

The oracle's probes check presence, not correctness — a file exists, a symbol appears, a
script is declared. `pnpm oracle status` saying `DONE` means the deliverable is on disk, not
that it works. Correctness is `pnpm gates`, the test suite, and the human approval gate, in
that order. A green oracle and a red gate means the gate is right.
